# 公开模板仓库独立站实施方案

> **执行约束：** 本文是经确认的新架构实施路线，不表示任何远端资源已发布。实施时逐阶段编写详细任务与测试；未经单独授权，不提交代码、不改变 GitHub 仓库可见性、不推送镜像或切换生产流量。

**目标：** 平台统一提供公开模板仓库及公共演示；每家公司自行部署 CMS 和网关，在自己的 CMS 选择、预览、引入模板并发布独立站，无需 R2 发布索引或每家公司配置模板拉取密钥。

**架构：** 公开 Git 仓库保存模板源码、不可变版本清单和审核记录；公开 GHCR 保存按 digest 引用的镜像。公司 CMS 拉取并验证指定版本清单，生成本站草稿及内容 Release；公司网关验证镜像身份并运行站点，向访客提供域名路由和已发布内容。CMS 与网关分服务部署，可以在同一公司主机上运行；平台不连接公司内网、不保存公司内容。模板目录/演示平台统一提供，实际“引入”在公司 CMS 内执行。

**技术栈：** Node 22、Nuxt、MongoDB、Docker/OCI、GitHub Actions、GHCR、公司侧 CMS 与独立网关。

---

## 已确认边界与当前状态

- 公司用户只在自身 CMS 授权引入和上线；公共演示不使用公司的内容、账号或密钥。公网仓库/镜像可匿名读取，只有平台维护者可以审核与发布。公开仓库会公开完整 Git 历史；GitHub 仓库可见性变更需要单独批准。
- 已上线站点固定 `templateId@version`、清单校验值、镜像 digest 和内容 Release；清单或镜像更新不能静默升级站点。平台必须保留仍被引用的历史版本和镜像。Git 分支或可移动 tag 不作为上线身份。
- 当前 `storefront-templates/.github/workflows/template-release.yml` 仅测试/构建；`scripts/publish.mjs` 的存储仅为内存实现，与公开 Git 清单方案不直接兼容。实施时重用校验逻辑，替换发布存储，不把内存 store 当成生产注册表。
- 当前 `cms/backend/src/presets/catalog.ts` 为内置目录，`import.ts` 以该结构生成模型和可选示例 Entry；公开模板的 `template.json` 尚无相同的 `theme`/`demo` 结构。需明确公开清单与 CMS 展示/示例数据的映射，不能直接把现有清单塞进导入函数。
- 当前 `cms/docker-compose.prod.yml` 的 `storefront-gateway` 只是 Nginx 代理，并非可部署模板、持久化发布状态的独立网关。新网关不可通过改名代替。现有站点及路由在迁移验证前保持原样。
- 原有设计 `docs/superpowers/specs/2026-10-25-gateway-managed-storefront-design.md` 和旧实施计划仍描述私有仓库/制品存储/集中注册表假设；本方案对**新开发**采用公开 Git + GHCR，旧设计中的隔离、故障回滚、发布快照和域名安全要求继续适用。

## 阶段 0：公开前审计与基线

**涉及：** `storefront-templates` 全部受跟踪文件及 Git 历史、`.gitignore`、`cms/backend/src/presets`、`cms/docker-compose.prod.yml`。

1. 只读清点 `git status --short`、`git ls-files`、全部可公开历史分支和标签；使用可信的 secret 扫描器对**历史和当前树**扫描凭据、客户数据、内部地址、版权/授权限制。对命中项人工确认；若真实密钥曾提交，先撤销并轮换，再决定是否重写历史；不能仅删除工作区文件或添加忽略规则。检查本地 `.env*` 不被跟踪，也不将其内容打印到日志。
2. 在 CMS 执行现有契约测试与 `npm run build:noEmit`，在模板仓库执行 `npm test`、`npm run validate`、镜像构建和独立烟测；在 Linux CI 补测 Windows 本地跳过的符号链接用例。记录当前站点/Release/域名行为和回滚基线。
3. 明确 GitHub 仓库公开后的许可与写权限、受保护默认分支和版本标签、必需审核/状态检查；扫描合格和授权确认前**不修改仓库可见性**。

**退出条件：** 敏感信息与许可审计通过；凭据风险已处理；回归基线留存；仓库公开由负责人另行授权。

## 阶段 1：平台模板发布与公开分发

**涉及：** `storefront-templates/templates/<id>/<version>/template.json`、`schema/template.schema.json`、`scripts/validate.mjs`、`test/publish.test.mjs`、`.github/workflows/template-release.yml`；可新增最小的机器可读已发布版本索引和发布校验测试，位置在模板仓库内。

1. 定义公开索引记录 `{schemaVersion,id,version,manifestChecksum,imageDigest,status}`；明确 SHA-256 的规范化 JSON 规则与 CMS 契约一致。每个已发布版本单独保存固定清单和镜像 digest；目录只列通过 CI 验证的版本。相同 `id@version` 不允许变更清单、资源或 digest；修复需发布新版本。索引只由受保护的发布 PR/CI 更新，失败时不得出现 `available` 记录。
2. 先写测试覆盖清单键/资源校验、固定版本重复发布、篡改后拒绝、未就绪镜像不可列出、并发或重复发布。将现有内存发布逻辑改为适合受保护 Git 的发布流程；不要让公司运行时相信未审核的任意分支、URL 或 tag。
3. CI 在审核合并后构建、扫描并运行镜像烟测，将镜像推送公开 GHCR；抓取远端 digest，建立可信构建身份/签名或等价可核验来源，验证后以受保护变更写入索引。只公开读取，不开放匿名写入；CI 使用最小权限的短期凭据。关闭已引用版本和镜像的自动清理。
4. 非生产验证匿名获取 Git 清单/索引和 GHCR digest、校验 checksum 与来源；验证重跑幂等、同版本修改被拒绝、未发布候选不出现在目录。平台公共演示仅用已审核镜像和演示数据，不接触公司 CMS。

**退出条件：** 首个候选版本从 CI 到公开清单及公开镜像完成真实端到端验证；用户无需登录即可读取，但无法修改；旧版本仍可取得。现有只跑测试的工作流不满足此条件。

## 阶段 2：公司 CMS 目录、预览与引入

**涉及：** `cms/backend/src/presets/catalog.ts`、`import.ts`、`controller.ts` 及对应测试；CMS 对应模板目录与引入界面。

1. 测试先覆盖：固定来源的索引获取与清单校验、兼容版本筛选、断网/篡改拒绝、已有站点不自动升级；目录可只读缓存上一次验证通过的结果，但不得把未验证的新版本作为可引入项。
2. 接入固定的公开发布源（非任意用户输入 URL）；把公开清单转换为当前 CMS 模型/页面导入契约，同时提供版本化的展示与可选示例数据；保留既有内置 preset 的兼容行为，避免破坏旧站。校验 schema、checksum、键、页面路径、媒体资源以及 CMS/Release 兼容版本。
3. 公司运维人员在自己的 CMS 浏览/预览已发布版本并确认引入；CMS 按所属工作空间创建模型、页面、Entry 草稿，记录版本与 digest；导入重试幂等且不会覆盖既有编辑。公共演示与公司草稿预览分离，后者必须鉴权且不对公网暴露草稿。

**退出条件：** 一家公司可在无 GitHub 凭据、无 R2 凭据情况下，从 CMS 完成已审核模板选择、预览、引入和编辑；断网或被篡改的清单不会被部署。

## 阶段 3：公司网关与发布链路

**涉及：** 独立网关仓库（地址见现有设计文档；实施前确认实际 checkout），CMS 发布/回滚接口及状态界面，`cms/docker-compose.prod.yml` 与公司部署说明。

1. 将网关作为与 CMS 分离的服务和权限边界：保存站点、域名、镜像 digest、Release 指针及发布操作状态；只接收鉴权、幂等的 CMS 发布请求。部署 worker 单独拥有容器运行权限，CMS 和公网接口不得接触 Docker Socket。两服务可以同机部署，但故障与升级边界分离。
2. 网关核验固定 digest 对应的公开镜像来源，从 CMS 获取并校验站点范围内不可变 Release，保存可独立服务的已发布快照；访客请求只能读此快照。先准备新实例和数据、检查健康及代表页面，再原子切流；失败保持旧实例/旧 Release，支持重试与显式回滚。
3. 首先开放平台子域名；自定义域名必须验证所有权、DNS 指向及 HTTPS 后切换。未知 Host 关闭访问，站点间数据/凭据隔离；CMS 失效时现有已发布站点继续可访问。保留旧共享 Storefront 路由直到逐站迁移并验证回滚。

**退出条件：** 两家公司分别部署 CMS/网关，两站可使用同一 digest 但内容互不可读；发布、升级失败、断网、CMS 宕机及回滚测试通过；域名/TLS/备份恢复与单机容量验收完成。

## 执行顺序与决策点

- 阶段 0 的审计和授权先于仓库公开；阶段 1 的真实发布先于 CMS 接入；阶段 2 完成后才能让公司用户引入；阶段 3 的网关健康切流验证先于对外上线。每阶段独立验收，禁止以本地测试替代远端发布或生产验证。
- 不再配置 R2 发布索引，原本用于该方案的本地 R2 配置不属于新链路；不要在新方案中读取或提交它。GHCR 镜像仍需存续、来源验证与发布权限控制。
- 若公开仓库历史审计不通过，不应为赶进度直接公开；停在阶段 0，先处理密钥与授权，再继续。不得静默将公司部署改为平台共享部署。
