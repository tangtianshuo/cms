# 所有模板的私密草稿预览

日期：2026-10-29。状态：方案待用户审阅，尚未实施。

## 目标与现状

用户要求所有模板均支持预览。覆盖整站已保存草稿、编辑器当前页未保存内容、桌面和移动视口，以及草稿站内导航。预览须使用对应模板版本的真实页面结构和样式。

当前 CMS 的 `ui/src/util/template-preview.ts` 仅允许 `aeroframe@1.0.3` 使用独立渲染器，其握手也固定该身份。内置 `atelier@1.0.0`、`market@1.0.0`、`aeroframe@1.0.0` 已有展示预览。Templates 仓库包含五个公开版本：AeroFrame 1.0.0、1.0.1、1.0.2、1.0.3，以及 FireGuard 1.0.0。后两个版本已有 `/preview`、父窗口校验、内存快照和过期机制，前三个版本缺少入口。

本方案涉及相邻 `Independent-Website-Templates` 仓库。已发布版本的生产镜像、manifest、registry 记录保持不可变；预览构建产物单独标识并部署。现有站点无需更换模板或升级才能获得预览。

## 方案选择

1. **推荐：统一协议、按模板和版本运行真实渲染器。** CMS 通用选择服务，模板侧统一构建和验收；可覆盖旧版并支持后续版本。
2. 共用 CMS 内置展示渲染器：改动小，但 FireGuard 等独立设计会失真，不符合真实预览目标。
3. 持续增加 CMS 模板分支：能接入 FireGuard，但每次增加版本仍要修改业务代码，旧版入口问题也未解决。

## CMS 服务选择

增加构建配置 `VITE_TEMPLATE_PREVIEW_RENDERERS`，格式为 JSON 对象：键为精确 `templateId@templateVersion`，值为独立预览服务的精确 HTTP(S) origin。整个映射只由受信任的部署配置提供，草稿数据不能指定服务 URL。

保留 `VITE_TEMPLATE_PREVIEW_ORIGIN` 对 AeroFrame 1.0.3 的现有兼容配置，精确映射优先。内置模板在没有显式映射时继续使用现有 `VITE_STOREFRONT_ORIGIN`；配置映射后使用真实版本渲染器。不可通过通配版本或回退到其他版本来冒充兼容。

解析时拒绝数组、非字符串、无效身份、凭据、路径、查询、片段和非规范 origin。显式存在但无效的目标配置须报告配置错误，不能悄悄改用其他服务。未知版本显示该版本缺少预览服务及管理员操作指引，不再要求更换 AeroFrame。

返回的 PreviewTarget 包含模板 ID、版本、显示名、mode、origin 和 notice。整站和单页共用解析器。所有页面必须具有一致的合法模板身份，空站点与混合版本明确报错。

## 消息协议与页面生命周期

独立渲染器发送 `{type:'storefront:preview-ready',templateId,templateVersion}`。CMS 验证实际 iframe source、精确 origin 及目标模板 ID 和版本；全部匹配后才发送私密快照。内置预览保留已有无身份握手，不扩大到其他模板。

CMS 仍发送 `{type:'storefront:preview',payload,path?}` 到精确 origin。渲染器验证配置的 CMS origin 和实际父窗口，并验证完整快照、路径和每页模板身份。模板版本是构建身份，不接受 URL 参数覆盖。

模板或版本改变时，即使 origin 相同，也必须清除 ready 状态并重新创建 iframe；旧握手不能授权新目标。整站和单页的连接文案改为当前模板名称和版本。超时有明确重试提示。关闭、卸载、刷新时清除快照和连接状态。

独立渲染器只在内存保存草稿，十分钟过期，退出销毁；响应保持 no-store、noindex、精确 frame-ancestors。预览服务不需要 Gateway 网站凭据，不开放草稿 HTTP API，也不把草稿写进浏览器持久存储或服务端日志。

## 所有现有模板的渲染能力

FireGuard 1.0.0 和 AeroFrame 1.0.3 使用现有真实组件及预览入口，纳入统一验收。

AeroFrame 1.0.0–1.0.2 通过独立预览构建准备器，从该版本源码生成临时构建目录：保留原样式和页面 template，将页面的数据入口适配为受校验的内存快照，增加统一私密预览壳及站内导航。源码中的已发布版本目录不就地覆盖，生产镜像不重新登记。适配器对已知结构做明确检查，结构不匹配即构建失败，不进行无约束的文本替换。

预览产物记录模板 ID、版本、原源码 commit、适配器版本和镜像 digest；与生产模板镜像分开命名。每个服务固定一个版本，避免不同版本的 Nuxt 资源和路由互相冲突。公共反向代理可通过独立主机名路由到各服务，CMS 仍使用精确 origin。

三款内置模板沿用与其当前生产展示共用的组件。完善内置预览的选定路径、快照更新后的导航状态、过期及清理，并验证与独立渲染器相同的草稿隔离要求。

## 后续新增模板

模板发布检查要求存在私密预览入口，握手身份与 manifest 一致，真实渲染器能够读取标准快照、隔离草稿、站内导航且拒绝外部消息。新模板通过这一合同接入，不再更改 CMS 的模板分支。

发布检查和部署登记是两个步骤：通过合同不意味着已有运行服务。上线模板的交付必须同时构建预览产物、运行服务、登记 origin 并配置 CMS 的 frame-src。CI 缺少合同测试或可用服务登记时不得声称该版本已具备可用预览。

## 单页未保存编辑

保留现有已保存整站快照加当前页覆盖策略，并应用于每个独立渲染器。保留已保存路径及关联卡片，覆盖对应语言的当前页内容，不修改源快照。

新建未保存条目、未绑定页面、未启用页面、语言不匹配或模板身份冲突继续显示具体保存指引，不虚构公开路径。站点设置编辑的当前页覆盖范围在界面明确说明，整站预览展示保存后的站点状态。

## 部署与回归

CMS Dockerfile、生产 release workflow、示例环境和操作文档传递统一映射。反向代理的 frame-src 仅列实际预览 origins。每个预览服务配置精确 CMS admin origin。映射、CMS CSP 和服务身份必须共同验证。

本地 Docker 验收同时运行真实 AeroFrame、FireGuard 和内置预览，并对旧版本完成构建及浏览器验证。部署切换前产出可审阅的镜像标识、配置、健康检查和回滚步骤；生产部署结果须单独记录，不把本地通过说成生产可用。

## 验收标准

- 三款内置模板、五个公开模板版本均可预览，FireGuard 保持消防设计和站点现有数据。
- 每个版本验证首页、分类、产品、内容页；覆盖已保存整站、未保存单页、私有媒体、站内跳转、移动布局、关闭重开和过期。
- 新增任意符合合同的模板，只需发布预览服务和登记映射，CMS 无需增加模板条件分支。
- 错误 origin、错误 iframe source、错误模板和版本、混合快照、无效映射、连接超时均不发送草稿；同 origin 下切换身份也不能复用授权。
- 未配置服务与服务不可用分别显示准确提示，不引导用户切换到其他设计。
- 预览操作不发布内容，公开站点保持原发布快照，既有站点和 immutable registry 不被改写。
- 运行相关单元测试、CMS UI 类型检查及构建、所有渲染器构建和合同测试，并保存真实浏览器验收证据。

## 交付顺序

1. CMS 通用映射、动态握手、两种预览入口和回归测试。
2. Templates 通用预览合同、现有版本构建适配、发布检查。
3. 内置预览生命周期补齐、完整本地部署及浏览器验收。
4. 生成生产配置、部署产物和验证记录，完成实际环境接入。
