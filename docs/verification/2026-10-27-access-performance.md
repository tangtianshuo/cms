# 正式站访问速度排查

排查时间：2026-10-27 22:06–22:10（Asia/Shanghai）。目标：`cms.novaintelligent.cn`。本次只读诊断，未修改生产配置。

## 结论

当前证据把主要耗时定位在公网传输链路，另有静态资源全局禁止缓存的配置问题放大其影响。服务器应用和内部代理没有复现相同延迟。尚未把公网故障进一步定位到具体运营商、代理节点、Cloudflare 边缘节点或边缘回源链路；不能仅凭这些样本认定 Cloudflare 服务本身故障。

浏览器 Network 中，主脚本等待约 2.3 分钟后出现 `net::ERR_CONNECTION_CLOSED`，页面未进入 Entry 编辑器。这是独立于 Entry 预览功能的页面启动阻塞证据。

## 分层测量

使用 curl，对同一个正式脚本 `/assets/index-e9d9eaf4.js` 测量，公网请求启用内容压缩。表内均为完整请求总耗时；超时样本只收到部分数据或未完成握手。

| 访问路径 | 主脚本耗时 | 结果 |
| --- | --- | --- |
| 服务器直连 CMS `127.0.0.1:18182` | 10 ms | 200，1,739,266 字节 |
| 服务器经过 relay `172.18.0.1:18184` | 31 ms | 200，1,739,266 字节 |

另一轮本机测量中，脚本直连耗时 14.69 s，经代理耗时 9.70 s。可见延迟和失败具有波动性；不能用单次成功排除问题，也不能认定代理是唯一原因。本机系统 HTTP/HTTPS 代理为 `127.0.0.1:7897`，终端默认没有代理环境变量，诊断分别显式测试直连和代理。

DNS 解析约 2–36 ms；TCP 多数约 0.3 s，部分 TLS 握手超时。首页本身仅约 1.1 KB，主脚本下载不完成时应用无法启动。脚本原始约 1.74 MB，压缩后约 0.53 MB，公网已有 zstd 压缩，不能把问题描述为公网未压缩。

## 已确认的缓存配置问题

已读取运行中 relay 的实际挂载配置，与 `deliverables/novaintelligent-deploy-20261027/relay.conf` 一致：CMS server 级设置 `add_header Cache-Control "no-store" always`，作用于 `/assets/` 的哈希文件。

正式脚本实际响应：

```text
cache-control: no-store
cf-cache-status: BYPASS
content-encoding: zstd
```

这使浏览器和 CDN 无法缓存主脚本，每次打开都重新经过公网并回源。源站 CMS 返回该文件时本来没有缓存头；全局禁止缓存来自 relay。

此外，生产边缘 Nginx 对全部请求设置 `Connection "upgrade"`，边缘及 relay 均全局关闭 `proxy_buffering`，配置偏向流式/WebSocket 请求。可以改进，但尚无对照实验能证明这些设置导致本次连接中断。

## 建议处理顺序

1. 对构建产生的哈希静态资源单独设置长期公共缓存，例如 `/assets/` 的 `public, max-age=31536000, immutable`。HTML、认证接口、预览内容继续采用各自合适的禁止缓存策略。上线后检查首次 MISS、后续 HIT，以及浏览器缓存命中。
2. 对比相同网络下的 IPv4、IPv6、代理及直连，确认实际浏览器出口；检查代理节点和 Cloudflare 边缘路由。当前 IPv6 样本更差，样本量不足以直接决定关闭 IPv6 或更改 DNS。
3. 缩减首屏主脚本体积，按实际依赖分析延迟加载；普通静态请求恢复合适的代理缓冲，WebSocket/流式端点单独配置。
4. 在页面启动恢复稳定后，继续检查 Entry 中实际 iframe 地址、CSP、预览 API 和消息握手。当前没有进入正式 Entry，因此不能宣称本次已经查明或修复预览功能根因。
